# G2 공통 계약

이 문서는 `임베디드 C++로 안전한 실행 기반 만들기`에서 코드가 반드시 지켜야 할 규칙과 자동 검사의 한계를 정리합니다. 검사로 확인한 사실과 학습자가 직접 설명해야 할 내용을 구분해 기록합니다.

## 고정 실행 환경

| 항목 | 계약 |
| --- | --- |
| Python | 3.12.13 |
| 실행 관리자 | uv 0.12.3 |
| C/C++ 도구 | ziglang 0.15.2의 `zig c++`·`zig cc` |
| 개발 PC | native x86_64 hosted C++20 |
| 공개 검사 | O0·O2, 경고 오류 처리, ASan·UBSan |
| 예외·RTTI | 2-1은 메모리 할당 실패를 오류값으로 바꾸기 위해 예외 허용; 2-2~2-4는 둘 다 끔 |
| 오브젝트 파일 분석 대상 | `thumb-freestanding-eabi`, `aarch64-freestanding-none` |
| ELF 판독 | pyelftools 0.32 |

개발 PC에서 실행한 sanitizer 결과만으로 Cortex-M, DMA, 실제 차량에서도 안전하다고 주장할 수는 없습니다. 독립 실행 대상은 빌드와 ELF 구조만 확인합니다. 실행 시간, 실제 동작, 메모리 배치는 아직 검증하지 않습니다.

## 입력 계보와 독립성

| 묶음 | 파일 | 쓰임 |
| --- | --- | --- |
| 공개 A | `fixtures/g02/sprint-2.*-v1.hpp` | 구현 중 빠르게 다시 확인 |
| 공개 B | `fixtures/g02/retest-2.*-v1.hpp` | 값·길이·부호·경곗값을 바꿔 재시험 |
| 봉인 C | 평가자가 별도 보관 | 종합 평가와 전이 확인 |

검사기는 `G02_SUBMISSION_ROOT` 아래의 구현 파일 네 개만 학습자 프로그램에 연결합니다. `reference/`는 공개 검사가 결함 주입본 10개를 모두 찾아내는지 확인할 때만 사용합니다. 학습자 구현과 기준 구현을 같은 프로그램에 넣었다면 그 결과는 인정하지 않습니다.

## 2-1 자원 수명 계약

- `MessageOwner`는 1–256바이트의 데이터와 32비트 순서 번호를 변경할 수 없는 저장 공간에 복사합니다.
- 빈 입력, 257바이트 이상의 입력, 메모리 할당 실패는 각각 알맞은 `OwnerError` 값으로 반환합니다.
- `MessageOwner`는 복사할 수 없고 이동만 할 수 있습니다. 이미 다른 객체로 이동한 `MessageOwner`에서 `lease()`를 호출하면 `MovedFrom`을 반환합니다.
- `PayloadLease`는 원본 저장 공간의 `shared_ptr` 소유권 관리 정보도 함께 보관합니다. `MessageOwner`를 이동하거나 컨테이너가 재배치되거나 큐에서 꺼낸 뒤 원본 객체를 파괴해도, `PayloadLease`가 살아 있는 동안에는 `span`이 유효해야 합니다.
- `PayloadLease`를 이동하면 소유권을 공유하므로 이동 전 객체와 이동 후 객체를 모두 읽을 수 있습니다. 참조 횟수를 관리하는 비용을 감수하고 선택한 정책입니다.
- `Result::value()`와 `error()`는 먼저 `has_value()`를 확인한 뒤 호출하는 precondition API입니다.
- 2-1에서는 힙 사용을 허용합니다. 이 규칙을 2-2의 “초기화 뒤 동적 메모리 할당 0회” 조건과 혼동하면 안 됩니다.

공개 검사는 원본 저장 공간의 소유권 관리 정보를 `weak_ptr`로 따로 관찰합니다. 수명이 끝난 데이터를 우연히 읽을 수 있었거나 sanitizer가 오류를 잡지 못했더라도, 원본을 소유하지 않는 `PayloadLease`는 통과하지 못합니다.

## 2-2 고정 용량 이벤트 처리기 계약

- `Event`는 16바이트 데이터, 16비트 종류, 32비트 순서 번호를 값으로 보관합니다. C ABI에서의 메모리 배치는 보장하지 않습니다.
- 큐에는 이벤트 32개, 콜백 목록에는 콜백 8개까지 들어갑니다. 객체를 만든 뒤에는 이벤트 추가, 콜백 등록·해제, 이벤트 한 건 처리 과정에서 C++ `new/new[]`를 호출하지 않아야 합니다.
- `RejectNewest`는 큐에 있던 32개를 그대로 두고 새 이벤트를 거부합니다. `DropOldest`는 가장 오래된 이벤트 한 건을 버리고 새 이벤트를 받습니다.
- 이벤트를 한 번 처리할 때는 처리를 시작한 시점에 큐에 있던 이벤트 한 건과 콜백 목록 사본만 사용합니다. 콜백 안에서 새로 넣은 이벤트는 다음 처리 때 꺼냅니다.
- 처리 도중 콜백을 제거해도 현재 목록 사본에서는 한 번 실행되고 다음 처리부터 빠집니다. 새로 등록한 콜백도 다음 처리부터 실행합니다.
- 콜백 함수와 사용자 데이터의 수명은 콜백을 등록한 쪽에서 관리합니다. 사용자 데이터는 콜백을 해제할 때까지 이벤트 처리기보다 오래 살아 있어야 하며, 콜백은 예외를 밖으로 던지면 안 됩니다.
- 콜백 핸들의 세대 번호가 `uint64_t` 최댓값에 닿으면 해당 칸을 더 이상 사용하지 않습니다. 오래전에 해제한 핸들이 다시 유효해지는 일을 막기 위한 조치입니다.
- reject·drop 진단 계수는 `uint64_t` 최댓값에서 포화합니다.
- 공개 함수 한 번은 큐의 최대 용량 32 또는 콜백 최대 개수 8을 넘지 않는 횟수만 반복합니다.

메모리 할당 검사는 C++ 전역 `new/new[]` 호출만 셉니다. 운영체제, C 표준 라이브러리, 검사 도구 내부에서도 할당이 전혀 없다고 주장할 수는 없습니다.

## 2-3 생산자·소비자 큐 계약

- 생산자 2개와 소비자 1개가 사용하는 용량 8의 큐이며, mutex와 condition variable로 동기화합니다. lock-free 구현은 아닙니다.
- `count/head/tail/closed`는 모두 같은 mutex를 잡은 상태에서 읽고 씁니다.
- 큐가 가득 차 기다리는 생산자와 큐가 비어 기다리는 소비자는 깨어날 때마다 대기 조건을 다시 확인합니다. 알림을 받았다는 사실 자체를 상태로 취급하지 않습니다.
- `close()`는 기다리던 생산자와 소비자를 모두 깨웁니다. 닫힌 뒤 `push`는 `Closed`를 반환합니다. 이미 들어온 값은 모두 꺼낼 수 있고, 마지막 값을 꺼낸 다음 `pop`부터 `Closed`를 반환합니다.
- `close()`는 여러 번 호출해도 안전합니다. 파괴 전에는 호출자가 모든 worker를 join해야 합니다.
- 공개 검사는 인위적으로 깨운 뒤에도 용량이 유지되는지, 큐가 가득 차 기다리던 생산자가 `close()`로 깨어나는지, 닫힌 뒤 남은 값을 모두 꺼낼 수 있는지, 고정 입력 100개에서 값의 누락과 중복이 없는지를 확인합니다.
- 고정 입력 100개만으로 가능한 모든 스레드 실행 순서를 검사했다고 볼 수는 없습니다. 문제가 되기 쉬운 두 가지 깨움 순서는 관찰용 훅으로 매번 같은 순서로 재현하고, 나머지는 실제 생산자 2개와 소비자 1개 사이에서 값이 보존되는지만 판정합니다.
- 시험용 관찰 함수는 큐의 mutex를 잡은 상태에서 호출됩니다. 이 함수 안에서 큐 API를 다시 호출하면 안 되며, 시험 순서를 맞추는 용도로만 사용합니다.

TSan, PREEMPT_RT, 우선순위 역전, hard real-time 상한은 이 실습의 검증 범위 밖입니다.

## 2-4 설계와 C ABI 계약

- 가상 함수, 템플릿·정적 호출, 함수 테이블로 만든 세 구현은 정상 처리, 시간 초과, 정리 함수 호출 결과가 같아야 합니다.
- 실행 기반과 맞닿은 C++ 코드는 `-fno-exceptions -fno-rtti`로 빌드합니다.
- C에서 공개하는 파일은 C17 컴파일러로 포함할 수 있는 `g02_abi_c.h` 하나뿐입니다. C++ 클래스, 객체 배치 구조, 예외를 C 쪽에 노출하지 않습니다.
- C 콜백은 성공 여부를 반환하고 실제 데이터는 출력 포인터에 씁니다. 정상 데이터가 음수여도 음수 오류 코드와 충돌하지 않습니다.
- `g02_runtime_create`가 성공하면 라이브러리가 불투명 핸들 내부의 객체를 만들고, 사용자는 같은 라이브러리의 `g02_runtime_destroy`로 해제합니다. 콜백 목록은 복사하지만 사용자 데이터는 빌리므로, 사용자 데이터가 핸들보다 오래 살아 있어야 합니다.
- `g02_runtime_run`은 한 스레드에서 동기식으로 실행합니다. 성공, 시간 초과, 콜백 실패 어느 경우든 정리 함수를 정확히 한 번 호출합니다. 실패하면 체크섬은 0으로 둡니다.
- 독립 실행 대상의 O2 오브젝트 파일은 모두 같은 Zig와 빌드 옵션으로 만듭니다. 가상 함수 예제에는 컴파일러가 호출 대상을 미리 확정하지 못하게 하는 교육용 장치가 들어 있습니다. 가상 함수 테이블과 재배치 정보를 관찰하기 위한 것일 뿐, 제품 코드에 적용할 최적화 방법은 아닙니다.
- 고정한 Zig 링커는 map 파일을 만들지 않으므로 공개 검사는 ELF의 `.text`, 심벌, 재배치 정보를 판정합니다. 다른 링커의 map 파일을 추가할 수는 있지만, 빌드 대상이나 옵션이 다른 결과를 한 표에서 단순히 순위로 비교하면 안 됩니다.

## 필수 결함 주입

| 실습 | 결함 | 공개 판정이 잡아야 하는 것 |
| --- | --- | --- |
| 2-1 | 101 | 원본 저장 공간을 소유하지 않는 `PayloadLease` |
| 2-1 | 102 | 마지막 바이트가 빠진 span |
| 2-2 | 201 | `RejectNewest`가 가장 오래된 이벤트를 버림 |
| 2-2 | 202 | 이벤트 처리 중 바뀌고 있는 콜백 목록을 그대로 순회 |
| 2-2 | 203 | 한 번의 이벤트 처리에서 콜백이 다시 넣은 이벤트까지 꺼냄 |
| 2-3 | 301 | 깨어난 뒤 대기 조건을 다시 보지 않아 큐 용량 초과 |
| 2-3 | 302 | `close()`가 큐가 가득 차 기다리던 생산자를 깨우지 않음 |
| 2-4 | 401 | 가상 함수 구현의 시간 초과 경로에서 정리 함수 누락 |
| 2-4 | 402 | 함수 테이블 구현의 시간 초과를 성공으로 잘못 반환 |
| 2-4 | 403 | C API의 시간 초과 경로에서 정리 함수 누락 |

기준 구현에 결함을 한 개씩 넣었을 때 공개 검사가 비정상 종료 코드나 제한 시간 초과로 모두 찾아내야 합니다. 결함을 두 개 이상 한꺼번에 넣어 우연히 실패한 결과는 인정하지 않습니다.

## 즉시 불합격

- 수명이 끝난 `span`, 해제한 메모리 접근, 데이터 경합, 큐 용량 초과
- `sleep` 시간을 늘려 동시성 검사를 우연히 통과시킴
- 이벤트 처리기의 금지 구간에서 동적 메모리를 할당하거나 예외를 밖으로 전파
- `close()` 뒤에도 끝나지 않는 스레드, 콜백 정리 함수가 0번 또는 2번 이상 실행
- C 헤더를 C17로 빌드할 수 없거나 C++ 객체 배치 구조·예외를 노출
- 개발 PC의 결과를 MCU 실행·하드 실시간·차량 적합성 근거로 표현
- 공개 입력 A·B만 다시 외워 봉인 평가를 통과했다고 표시

위 항목이 하나라도 있으면 점수와 상관없이 재시험합니다.
