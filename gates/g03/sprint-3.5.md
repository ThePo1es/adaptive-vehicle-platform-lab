# 실습 3-5 — 컴파일러 문제로 의심되는 사례를 최소 예제로 줄이고 신고 여부 판단하기

> 상태: `Runnable` · [장 안내](README.md) · [실행 계약](contract.md)

## 시간과 기준 자료

능동 작업 19시간, 도구 실행 4시간, 동료 검토 대기 7시간으로 모두 30시간을 잡습니다. [LLVM 결함 생애 주기](https://llvm.org/docs/BugLifeCycle.html), [LLVM 결함 신고 안내](https://llvm.org/docs/HowToSubmitABug.html), 대상 프로젝트의 기여 안내와 행동 규범을 읽습니다. 이미 공개된 문제를 재현할 때는 주소와 확인한 커밋을 기록합니다.

## 시작 조건

다음 후보 중 하나를 고릅니다.

- 고정된 컴파일러 버전에서 재현되는 공개 문제
- 차량용 코드에서 발견한 의심스러운 진단·최적화·백엔드 동작
- 최근 수정된 상위 프로젝트 회귀를 이전 커밋에서 재현

원본 코드의 UB, 잘못된 선택 사항, 대상 불일치를 먼저 배제합니다. 실제 신고는 동료 검토를 받은 뒤 진행합니다.

## 안내 실습

공개된 알려진 문제 하나를 지정된 버전에서 재현하고 입력을 줄입니다. 한 단계씩 코드를 없애며 증상이 유지되는지 자동 스크립트로 확인합니다.

## 독립 실습

새 후보를 분류합니다. 기대 동작의 근거, 처음 재현된 버전, 최소 재현 코드, 정확한 실행 명령, 실제 출력, 대상 환경을 한 묶음으로 정리합니다. 직접 고칠 수 있다면 실패를 재현하는 시험부터 작성합니다.

## 전이 과제

검토자가 재현 코드의 형식, 최적화 단계, 대상 중 하나를 바꿉니다. 90분 안에 문제 범위가 프런트엔드, 최적화기, 백엔드, 어셈블러·링커, 원본 코드 계약 중 어디에 있는지 다시 좁힙니다.

## 판정 기준

- 새 환경에서 한 명이 명령 하나로 증상을 재현
- 최소 재현 코드와 축소 기록이 있음
- expected behavior가 언어·IR·ABI 문서 절에 연결됨
- 문제를 신고하지 않아도 시험 우선 분석과 동료 검토가 완료됨
- 상위 프로젝트 의견을 받았다면 반영 여부와 이유를 기록

## 보고 전 확인

1. `creduce`, `llvm-reduce`를 쓰기 전에 증상을 판정하는 스크립트를 만듭니다.
2. 컴파일러 중단, 잘못된 코드, 놓친 최적화, 부족한 진단을 구분합니다.
3. 이미 보고된 문제인지 문제 추적기를 검색합니다.

## 보고를 멈추는 조건

UB를 컴파일러 결함으로 보고했거나 재현을 확인하기 전에 상위 프로젝트에 신고했다면 절차를 멈춥니다. 알려진 회귀 하나를 지정 커밋에서 재현하고 기존 시험이 판정하는 조건부터 읽습니다.
