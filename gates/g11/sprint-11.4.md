# Sprint 11.4 — 처리·활성화·헬스 검사·롤백

## 시간과 기준 자료

32–44시간을 배정합니다. R25-11 UCM·State Management·Execution Management 문서, P03의 Function Group State 계약, P04 기준 상태 모델을 사용합니다. 활성화 가능한 차량 상태와 프로세스 목록을 실행 전에 동결합니다.

## 상태 계약

`Received → Verified → Processed → ReadyToActivate → Activating → HealthChecking → Committed/RolledBack/RecoveryRequired`를 로컬 상태로 둡니다. 이름이 R25-11 상태와 정확히 일치하는지는 매핑 표에서 따로 판정합니다. 영속 쓰기마다 이전·새 record 중 무엇이 부팅 가능한지 정합니다.

## 안내 실습

Update Function Group 요청, 관리 프로세스 정지, 새 slot 선택, 재부팅, 헬스 검사, commit을 하나의 전이 ID로 연결합니다. 부팅은 저장된 운행 상태를 그대로 복원하지 않고 `Startup`에서 시작해 버전, 프로세스 목록, 차량 조건을 다시 확인합니다.

## 독립 실습

모든 영속 경계의 직전과 직후에 프로세스를 강제 종료합니다. 실제 보드에서는 선택한 지점의 전원 차단을 별도 결과로 기록합니다. 헬스 검사 실패, timeout, 호환되지 않는 의존 클러스터, 롤백 실패를 시험하고 마지막 정상 slot 또는 `RecoveryRequired`로 수렴시킵니다.

## 전이 과제

봉인 event는 활성화 중 `Driving` 요청, 새 서비스의 major version 불일치, 헬스 보고기 crash 중 하나를 겹칩니다. 생명주기와 상태의 결정 책임자가 내릴 판단을 먼저 표로 작성한 뒤 실행 결과와 비교합니다.

## 판정 기준

- 금지된 Function Group State에서 활성화가 시작되지 않음
- systemd, P01, P03, UCM 중 프로세스 재시작 실행 주체가 하나만 존재
- 모든 종료 지점이 이전·새 확정 slot 또는 명시된 복구 상태로 수렴
- 부팅이 항상 `Startup`에서 현재 조건과 프로세스 목록을 재검증
- 헬스 검사 전에는 새 버전을 확정 상태로 기록하지 않음
- 의존성·서비스 호환 실패가 정해 둔 시간 안에 롤백으로 이어짐
- 프로세스 강제 종료 결과와 실제 전원 차단 결과를 같은 근거로 섞지 않음
- R25-11 UCM 매핑과 로컬 A/B 단순화가 릴리스 노트에 남음

## 확인할 함정

- 저장된 `Driving` 기록은 다음 부팅의 현재 차량 상태로 쓰지 않습니다.
- 애플리케이션이 건강하다는 판단과 slot을 영구 확정하는 결정은 별도 사건입니다.
- 롤백 경로도 업데이트 대상이면 독립된 복구 신뢰점이 필요합니다.

## 활성화 판정 보류

헬스 검사 전에 commit하거나, 부팅 직후 저장된 운행 상태로 들어가거나, 두 구성요소가 동시에 재시작하면 G11A를 통과할 수 없습니다. 패키지와 프로세스를 하나씩만 남겨 모든 상태의 강제 종료 시험을 다시 실행합니다.
